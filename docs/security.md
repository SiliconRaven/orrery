# orrery 安全模型

语言：**中文** | [English](security.en.md)

本文定义 orrery 原生协作版在本机环境下防护什么、不防护什么，以及问题严重度分级。安全漏洞上报流程见根目录 [SECURITY.md](../SECURITY.md)。

## 核心责任边界

- **执行权限归各原生 Harness**：orrery 是一个纯本机的消息路由与协作 Hub，不替模型运行轮次，也不托管模型工具执行。每个群员运行在你自己的原生应用（Claude Code、Codex、Cursor、DeepSeek Harness 等）里，继承你本人在该应用中的账号、权限档位与审批配置；orrery 不替用户放宽权限（不开启自动批准/bypass），也不保证每次操作必定弹出审批确认。
- **跨 Agent 误导与间接提示注入风险**：经 Hub 投递进原生对话的消息（包括其他 Agent 的回复、插件消息，甚至经协作页发出的用户消息）在安全模型上都可能带有错误结论或恶意提示注入。**请勿把经 Hub 转来的消息当作你在原生应用里亲手下达的最终授权**；涉及修改规则/配置、执行敏感命令、提交或审批关键操作时，应在原生应用中亲自核对后确认。
- **跨厂商数据流转**：把多个不同厂商的 Agent 拉进同一个群后，一个 Agent 的输出可能通过群聊转发进入另一家厂商的上下文。请自行评估涉及敏感代码、密钥或隐私数据时的跨供应商合规要求。

## 运行边界与信任前提

签名接入的共享密钥存于私有登记处，Windows 核对 DACL，POSIX 核对所有者和权限位。签名绑定实际端口、路由、身份、正文和启动 claim，并在状态变更前检查时效及重放。设置可关闭 Hub 对明文的接收。静态 HTTP 宿主仍可能把明文发给占用端口的其他进程。回应未签名，残留锁回收有已知竞态。 [原生模式](native-mode.md)

- **仅绑定回环网络**：Hub Web 服务与 MCP 端点只监听 `127.0.0.1`，不向局域网或公网开放，发往 Hub 的本地请求不经过代理。
- **认证隔离与跨站防护**：
  - Web 静态页面无需登录即可读取，但所有 `/api/*`（含 `GET /api/health`、`/api/stream`、文件下载和 `POST /api/shutdown`）均需 API Bearer 令牌或经 `POST /api/session` 建立的 `HttpOnly; SameSite=Strict` 会话 Cookie，未认证统一返回 `401`。令牌保存在 `<ORRERY_HOME>/api-token`（或由 `ORRERY_API_TOKEN` 提供），用于阻止同机**其他操作系统账户**经 `127.0.0.1` 访问你的 Hub。
  - `/api/*`、`/mcp` 和 `/bridge/*` 均校验 `Host` 与 `Origin`（唯一例外是第三方受限插件沙盒 iframe 携带 `Origin: null` 读取 `GET /plugin-ui/<frameId>/…`，仅限不可猜测的会话帧 ID 且只读），`/api/*` 写请求必须为同源 JSON，阻断浏览器跨站调用本地 Hub。
  - 原生 `/mcp` 调用方先过请求认证：orrery 自带桥和插件发签名 `x-orrery-sig`（绑定 Hub、本次启动、端口、身份头和正文，不传密钥原文）；无法签名的静态 HTTP 配置（Codex、ZCode、Antigravity 的 MCP 配置）发明文 `x-orrery-bridge`，可在「设置 → 投递」关闭兼容。认证后再结合宿主可控上下文认人（Codex 仅传密钥与运行时 `_meta.threadId`，**不传** `x-orrery-session` 或 `x-orrery-harness`；Claude/DSH/WorkBuddy/Cursor 经桥或 Hook 传会话头；ZCode/Qoder 依赖运行时 `_meta`；Antigravity 依赖 Hook HMAC 签名 `orreryCaller`）。`Authorization` 头在 `/mcp` 上不代表任何群员。
- **零侵入原则**：
  - 不自动安装、启用、修改第三方应用（Claude、Codex、Cursor、DSH、Kimi、ZCode、Qoder、WorkBuddy、Antigravity）的用户配置、插件或登录状态。
  - 只往集群明确接入的目标会话写入投递；读取本地对话列表采用只读访问或临时副本，不修改原始会话库（原生对话自身运行仍会按目标应用机制落盘其会话历史）。
- **不主动启动用户原生应用**：Hub、适配器、桥和插件绝不拉起未运行的桌面客户端。唯一例外是 Electron 桌面外壳：用户在可信标签栏的 `+` 面板里亲手点一个没在运行的受支持应用时，外壳不带参数、不经 URL 协议启动它（见[桌面外壳](desktop.md)）。应用退出即离线，离线期间不投递、重新上线也不补发；唤醒链接仅在确认运行中实例能接收它时才触发（检查到系统分发之间的极短时间窗口为已知残余风险）。
- **Kimi 令牌例外**：`~/.kimi-code/server.token` 仅留在内存，且在 Windows 核验进程映像（`Kimi Code.exe` / `kimi.exe`）与 `netstat` TCP 监听 PID 一致后，方经无代理回环请求发往本机实例，绝不写日志、事件或数据库。

## 主要防护范围

1. **消息诱导越权防护**：
   - 群员权限不超过用户在原生应用里的自身配置；Hub 不替用户开启自动批准，只向明确选中的会话投递，且永不自动启动未运行的应用。
   - 经 Hub 投进原生对话的消息在原生应用中带有来源标记（或显示为来自外部会话），提示模型将其视作协作请求而非用户在原生应用内直接点击批准。
2. **禁止未授权网络访问与跨站调用**：回环绑定、API 令牌 / 会话 Cookie、Bridge 签名与同源 JSON 校验阻断局域网、公网和第三方网页越权访问。
3. **防止同一系统内会话冒充**：模型无法在 MCP 工具参数中自称别的群员；非签名通道的模型参数不作身份依据。
4. **防循环与花费失控**：
   - 内置单消息链**最大转发跳数**（默认 `6`）、**单链最大轮次**（默认 `20`）、**每个成员每小时最大轮次**（普通成员默认 `30`，启用中的协调员默认 `120`，系统通知批次独立兜底每小时 `300` 批）以及**全局暂停投递**总开关（详见[防循环与限流](hop-limit.md)）。
   - 跳数上限与单链轮次上限允许用户在网页设置中显式改为无限（写入需带 `confirmUnlimited: true` 并经警告确认，仅防误操作）；**每小时轮次上限与暂停开关始终生效、无法关闭**，确保即使放开前两项也不会失控循环。
5. **桌面版外壳窗口与启动边界**（[桌面外壳](desktop.md)）：
   - 仅对用户在可信标签栏明确选择、每次写前均重新核验身份（句柄、PID、完整映像路径、类名、顶层无 owner）的已运行顶层窗口调整位置、大小、最小化/还原与前后顺序；窗口失效或重启后必须由用户重选。
   - 不嵌入第三方窗口、不改窗口样式或 owner、不注入键盘/鼠标输入、不关窗口、不结束进程。
   - 协作页没有 `preload`、没有任何 Electron/Win32 IPC、所有浏览器权限默认拒绝，且拦截外部链接与 `window.open`；启动应用仅限用户在可信 `+` 面板点击受支持应用，不传参、不经 URL 协议，且每次使用保存路径前重新校验（已知残余风险：同账户程序可改写外壳数据目录中的 `app-paths.json` 或替换同名 `.exe`）。
6. **成员隐身协作开关（`hiddenAt`）**：隐身是协作开关，**不是保密边界**。Hub 强制保证：隐身期间拒绝向该成员投递新消息、拦截其一切 MCP 工具调用（含读取工具一律返回提示并空操作）、阻止向其派发新任务或 `@` 唤醒，并从其他普通成员的活跃成员列表（`list_agents`）与新通知展示名中隐藏它。不保证保密：其历史发言、既有任务记录中的成员 ID 仍可能让其他成员推断其存在，外部插件事件也不按隐身过滤，且不会打断已运行的轮次或阻止该成员在原生应用中直接访问本机文件。
7. **文件和图片防护**（[文件与 Skill](files.md)）：
   - 仅当文件头魔数确认为 PNG、JPEG、GIF 或 WebP 时才允许页面内联展示；其余文件（含 SVG、HTML）一律强制按 `application/octet-stream` 附件下载，并附 `nosniff`、`default-src 'none'; sandbox` 与 `Cross-Origin-Resource-Policy: same-origin`。
   - 原生成员通过 `send_message` 的 `attachments` 附带发件箱副本时，仅接受调用者自己发件箱目录内的纯文件名，禁止目录分隔符、UNC/扩展路径、符号链接与多硬链接，并按文件身份阻止把 Hub 密钥、`api-token`、`hub.json` 或数据库作为附件发出；Hub 只复制，不改动或删除原件。
8. **Markdown 防脚本执行与自动外传**：
   - 协作页与星图消息正文均由结构化 Markdown 解析器生成数据，再通过 DOM 节点构建（禁止 `innerHTML`），消息中的原生 HTML 一律按纯文本显示。
   - 链接仅接受规范化后的 `http:` / `https:` 协议并附加 `rel="noopener noreferrer"`，`javascript:`、`data:`、`file:` 等全部按纯文本展示。
   - 禁止自动加载消息中的远程图片（防止借跟踪像素外传信息），仅由用户显式点击打开；对块/行内嵌套深度和超长正文设解析上限，防止病态消息卡死页面。
9. **防止成员绕过独立验收**：任务的验收档位由用户或协调员定档，成员不可私自降级。验收者接手（[协作与任务流程](collaboration.md)）后转为自查档仅允许用户本人操作或群已显式开启对应开关，且绑定至唯一执行者，MCP 无权修改该群设置。
10. **回收站彻底清理**：`POST /api/clusters/:id/purge` 清除软删除集群的全部消息、任务与无主附件；依赖 SQLite 页机制，不保证物理盘底层扇区零擦除。未运行清理钩子的插件可能保留自有数据，结果会如实说明。
11. **只读 Git**：Hub 读成员项目里的 Git 仓库（分支候选、任务分支关联、提交时自动关联、接手与 `ship_fix` 产品代码变更范围核对、ship 结果核对）时只用只读子命令（`worktree list`、`rev-parse`、`for-each-ref`、`merge-base`、`log --no-merges --no-ext-diff --no-textconv --name-only`、`rev-list`、`diff-tree`、`config --get`），不取远端、不改引用和配置；**绝不运行 `--remerge-diff` 或任何会触发仓库 `merge.*.driver` / 外部 diff / textconv 的命令**，无法安全判定时回落为 `unverified` 保守知会；环境中禁用懒抓取（`GIT_NO_LAZY_FETCH=1`）、全部传输协议（`GIT_ALLOW_PROTOCOL=none`）和交互凭据提示，超时结束整个进程树。
12. **技能与 MCP 页只读出必要字段**：读取各应用的 skill 和 MCP 配置时，仅返回 skill 名字与描述，以及 MCP 服务器的名字、传输方式和目标（程序文件名或 URL 的协议与主机）；参数、环境变量、请求头和密钥从不读出。安装 skill 只写共享 skill 文件夹，拒绝链接，仅用户可调用（见[文件与 Skill](files.md)）。
13. **官方插件签名更新与第三方插件分级**：官方插件独立更新核验固定 ID、内置公钥与载荷签名（[官方插件](plugins.md)）；第三方插件按「受限」与「完全信任」两档承诺，见下文两节。

## 已绑定会话的正文

星图是默认关闭的官方插件。启用并重启 Hub 后，已认证的网页可通过 `GET /api/clusters/:cid/members/:mid/transcript` 读取本群活跃成员的已绑定原生会话。路由先验证成员归属和参数，再返回核心的分页结果。正文响应为 `Cache-Control: no-store`。关闭并重启后该路由返回 404；受信任插件仍可使用核心的进程内读取接口。

Orrery 私聊记录供用户和发送时绑定的收件人会话读取，群聊、共享任务和受限插件均无法访问。换绑会取消待发私聊，旧记录仍供用户查看。已确认的完全信任插件具备用户等价的访问权限。

除会话列表、标题和用量外，官方插件和用户确认过的完全信任插件可以调用 Hub 的进程内方法，读取群员当前绑定的原生对话正文（[架构说明](architecture.md#读取群员当前绑定的原生对话)）。调用方只给成员 ID；Hub 从自己的成员记录取得应用和会话，在异步读取前后都核对绑定，成员被移出、换绑或群进回收站后，旧绑定的结果不交给调用方。适配器以应用的数据目录为边界核对实际读的文件。

每次调用读一页，结果只在内存里返回。核心没有读正文的网页、MCP 或受限插件接口，也不把正文写进数据库、事件和日志。识别到 orrery 投递或群员发言时，Hub 用当前成员、所在群和自己的消息记录核对关联，缺少证据时保留原生条目、不推断消息编号。思考内容只显示应用提供的可见摘要或占位。

没有可信标记的应用（投递出现在等待命令结果、`system` 记录或无标记的用户记录里），适配器只交出未核实的投递候选（投递号、信封或直发正文，规则见[架构说明](architecture.md#读取群员当前绑定的原生对话)）。Hub 只在自己的投递记录证实这条消息真的投递给了这个成员、且在该成员所在的群里时才把条目显示为投递，否则原样保留。已接受的局限：在这些应用里，用户手打的文字若与真实投递给该成员的信封或正文完全相同，会显示成那次投递；显示的内容取自 Hub 里的真实消息，别的群或别的成员的内容不会出现。

- **Kimi Code**：只读取绑定会话在 `sessions/` 目录内的 `agents/main/wire.jsonl`（先经同目录 `state.json` 核对会话 ID 并拒绝链接与硬链接），从不读取 `server.token` 或连接本地服务；思考块仅输出占位，不返回原文。
- **DeepSeek Harness**：会话日志是多帧 zstd，解压逐帧进行并有上限（压缩文件超过 32 MiB 不读，单帧输出 4 MiB、解码窗口 8 MiB，每页 8 MiB 或 1024 帧），防止解压炸弹。投递只凭插件设下的请求 id 认出：Hub 只在它是投给这个成员的真实批次时才认；正文从不作为证据，没有请求 id 的记录从不当作投递，亲手打出的信封或直发正文仍是用户输入。能伪造的只有用 DSH 的会话接口以一个已知的真实投递 id 再发一条，结果也只显示本来就投给这个成员的消息正文。见 [DeepSeek 适配器](adapters/deepseek.md#读原生对话)。
- **ZCode**：正文在它自己的 SQLite 库里，原处只读打开，不复制整个库，也不写任何文件（做法、实测结果和剩下的一个竞态见 [ZCode 适配器](adapters/zcode.md#读对话原文)）；库文件及其 `-wal`、`-shm` 必须是 ZCode 目录下的普通文件，链接和硬链接一律拒绝；只查绑定会话的行。投递证据只取自整份读出等待命令输出、带这个会话票据的 `Read` 结果，用户自己输入的文字长得像信封也不算。
- **Qoder**：正文在应用自己的 SQLite 库里，用和 ZCode 同一个读取器在原处只读打开，不复制、不写任何文件（有 `-wal` 缺 `-shm` 时不打开、返回 `unsupported`，剩下的一个竞态同 ZCode）；库文件及其 `-wal`、`-shm` 必须是 Qoder 数据目录下的普通文件，链接和硬链接一律拒绝；会话 ID 必须是 UUID，只查绑定会话的行。投递证据只取自一种 `Read` 结果：这一轮所等的后台任务是这个会话自己运行、逐字等于本会话票据的等待命令，`Read` 整份读出这个任务的输出文件；用户自己输入的文字、别的会话的票据、别的工具的输出都不算（见 [Qoder 适配器](adapters/qoder.md#读对话原文)）。
- **Cursor**：只读取 `<cursorHome>/projects` 内绑定会话的 `agent-transcripts/<id>/<id>.jsonl`（拒绝非法 ID、链接与硬链接），绝不打开任何 `state.vscdb`；仅在首行带 8 位交接号标记时提交给 Hub 核实投递（未命中保留为 `user`），`thinking` 仅输出占位，无 `tool_result` 故不猜测 `orrery_post`。
- **WorkBuddy**：只读取 `<workbuddyHome>/projects/<proj>/<sessionId>.jsonl`（排除 `subagents/`，核对 `session-meta.sessionId` 并拒绝链接与硬链接，不打开 `workbuddy.db`）；`reasoning` 仅输出占位；仅匹配本会话等待票据的 `TaskOutput`/等待命令结果提交投递候选，无关工具与用户输入不被误认，直接与 `DeferExecuteTool` 的 `send_message` 经 `callId` 核对后对回发言。
- **Antigravity**：只读取 `<geminiHome>/antigravity/brain/<uuid>/.system_generated/logs/` 内 `transcript_full.jsonl`（仅缺省时回退 `transcript.jsonl`，拒绝链接与硬链接且不回退；不读 `.pb` 与 `conversations/*.db`）；`thinking` 仅占位并剥离脱敏 `orreryCaller` 签名；仅 `SYSTEM_MESSAGE`（`sender=system`、`MESSAGE_PRIORITY_HIGH`）提交投递候选，`USER_INPUT` 永不晋升，`call_mcp_tool` 成功结果按位置 `callId` 核对发言。

## 桌面版自更新

桌面进程从官方 GitHub Release 获取 Windows x64 安装包，限制下载来源并检查文件大小。下载后和启动安装器前都核对 SHA-256。只有用户在可信桌面设置中确认才启动安装器。

## 受限的第三方插件

受限插件（[第三方插件](external-plugins.md)）运行在独立的系统进程里，经 stdio 协议和 Hub 通信。`permissions`、事件授权、`clusterIds`、`writeClusterIds`、工具和界面位置授权只约束它**经 orrery 协议**能做的事：

- **读取和事件**：只在授予的群和类型内；授予事件类型就是授予读取它的内容（例如任务的标题、范围、意见和提交号），通配符包含以后新增的类型。消息正文另需 `messages.read`。事件队列有上限，卡死的插件只丢自己的事件。
- **发言**：需要 `messages.send` 和单独的写入群；唤醒成员另需 `messages.mention` 和用户打开的开关，并遵守暂停、防循环和限速。插件消息署名 `plugin:<id>`，成员应把正文当队友的请求处理。
- **发言检查**：只能拒绝群员的发言，不能改写；每次拒绝都在群里留记录；插件不回答时放行（fail-open）并留记录，所以坏掉的插件不能让群失声。
- **命令**：只有用户能运行；运行不写群聊、不唤醒成员。
- **群员工具**：调用者只由桥给的会话认出，参数按声明检查，回答之后再认一次调用者；每次调用都留一条只有元数据的记录（不含参数和结果内容）。回答会进入群员的上下文，应当作不可信的工具输出。
- **网页与标记**：网页在 `<iframe sandbox="allow-scripts">` 里，来源不透明，读不到 cookie、令牌、协作页和存储，调不到 Hub 接口，只能经页面和自己的插件进程通信；文件只从插件的 `ui/` 提供，地址里的界面 ID 随界面关闭、插件停止或 Hub 重启失效。标记由 orrery 画成虚线框并带固定的第三方插件图标，插件只给文字。已知边界：框架隔离不防插件进程把数据发出去，WebRTC 是否被挡住尚未验证。

**进程分离不是安全沙箱。** 插件以同一操作系统账户运行，能绕过协议直接访问该账户的文件、网络和程序（包括 Hub 的文件）。只运行可信代码。

## 完全信任的第三方插件

完全信任插件（[第三方插件「完全信任的插件」](external-plugins.md#完全信任的插件)）在用户确认后和官方插件一样在 Hub 进程里运行，和 orrery 本身权限相同。

**这一档保证的**（违反按 P1 处理）：

- **确认之前一行代码都不运行**：登记只让设置页出现一张卡片；用户确认之前、撤销之后、`ORRERY_SAFE_MODE=1` 时，Hub 不导入它的入口、不跑它的迁移。
- **只有用户能确认，确认绑定入口文件的真实路径**：确认接口要 API 令牌和同源 JSON，插件协议、MCP 工具和沙盒框架都写不了；入口换了位置就要重新确认。
- **可诊断的加载失败只跳过这个插件**：导入失败、导入和默认导出合计 10 秒内没完成（异步卡住）、插槽冲突、路由不在 `/api/x/<id>/` 下、迁移越出 `x_<id>_` 前缀、升级前备份失败，都只跳过这个插件和依赖它的插件，Hub 照常启动。同步阻塞不在此列，见下面“不保证的”。
- **页面只加载这次允许的网页模块**：只导入 `trustedFrontend` 列出的模块，文件只从它自己的 `webEntry` 文件夹提供，不给 HTML 和 Hub 入口。
- **信任结束时已打开的页面就地卸下它**：不再调用它的插槽、移除它加入的元素、调用它的 `onDispose`，页面不自行刷新，不丢用户没发出的输入。
- **永久删除群不假装删干净**：没运行清理钩子的插件，结果写明它的表里可能还有这个群的数据。

**不保证的**（由安装插件的人负责）：插件能读写数据库里的任何数据，能绕过防循环、暂停和投递记录，也能自己启动程序；“用户能看到每个成员收到了什么”对它不成立。插件自己的定时器和未处理的 promise 拒绝可能让 Hub 退出，死循环会卡住 Hub。刷新页面之前，它的网页模块代码仍在页面内存里。卸载后它的表留在数据库里；升级前的自动备份可以用来回退，但 Hub 不会自动还原。

## 不在防护范围内（Non-goals）

- **拥有同操作系统用户权限的恶意本机程序**：能直接读取登记处的 `bridge-secret`（默认 `~/.orrery/registry/`）、`~/.orrery/secret`、`api-token`、`hub.json` 或篡改插件文件、`plugins.json` 的本机程序与当前用户同权，不属于本威胁模型防护范围。
- **用户自行开启的全自动审批**：若用户在原桌面端开启自动运行命令/工具，来自集群的 `@` 将自动执行。
- **跨 Agent 误导与提示注入**：在正常权限范围内，Agent 被其他群员或外部输入说服后执行的操作由各原生应用审批机制把关。
- **用户自己安装的插件**：受限插件的进程和完全信任插件的代码按上面两节的说明运行；它们按“不保证的”做了坏事，不算 orrery 的问题。
- **第三方应用合规与云端行为**：各外部客户端服务条款（如 Antigravity 风险提示）与供应商服务端行为由用户自行评估。

## 问题严重度分级

- **P1（阻断级）**：可利用的安全漏洞、身份冒充、越权主动启动第三方应用或导致数据损坏丢失的问题，必须修复并复核通过。
- **P2（主要问题）**：明显影响稳定性、错误边界或功能契约但无直接安全/数据丢失风险的问题。
- **P3（加固项）**：超出本威胁模型的纵深防御建议与理论边界。
