# 协作与任务流程

语言：**中文** | [English](collaboration.en.md)

协作能力由 `tasks`（`src/plugins/tasks/`）、`coordinator`（`src/plugins/coordinator/`）与 `bookmarks`（`src/plugins/bookmarks/`）三个内置官方插件协同提供。接口字段见 [协作与任务 API](collaboration-api.md)。

## 成员角色与权限

集群内的任务操作受角色约束，用户始终拥有最终控制权：

| 角色 | 说明 |
|---|---|
| `coordinator`（协调员） | 每个群最多启用 1 位协调员，负责统筹、指派、调整验收配置及跟进停滞任务；不得自审代码，也不可兼任同一任务的执行与独立验收工作。 |
| 普通成员 | 领取或被指派任务、推进执行并提交验收；可充当另一位成员任务的独立验收者。 |
| `user`（用户） | 最高裁决者，可直接创建、改派、审批方案、直接通过/退回，或手动标记任务完成/合并。 |

业务角色带名称和说明描述（新建群默认附带“设计者、验收者、执行者”），可按角色限制任务执行或验收资格。

在任务工作台「角色与协调 → 任务权限」中，用户可为建任务、执行和验收分别选择本群业务角色。某项为空时所有成员都可操作。列表有角色时，成员持有其中任一项即可通过群级检查，任务自己指定的角色仍须全部满足。设置影响后续派工、开工和成员验收。已经开工的成员可照常提交，自查沿用执行资格。用户通过网页管理和验收时不受自己的角色限制，指定的成员仍须符合资格。

启用的协调员默认也须满足建任务角色。在协调员授权的「任务规划」下，用户可另行开启「建任务不受群级角色限制」。该选项默认关闭。开启后仍须拥有任务规划授权，只建议模式仍只生成建议。

群级任务权限仍引用的角色会返回 `ROLE_IN_USE`。用户先从「任务权限」移除该角色，再删除它。关闭任务插件期间，已保存的权限仍受保护。

## 任务状态与三档验收

每个任务按群内自增序号 `#<number>`（如 `#1`）标识，主要状态如下（`pending`、`working`、`review`、`completed`、`merged`、`cancelled`）：

```text
pending -> working -> review -> completed -> merged
             ^          |
             +-- reject-+

release -> pending
cancel  -> cancelled
reopen  -> pending
```

> 注：用户方案审批（`requiresApproval` / `proposalState`）、求助阻塞信号（`attention`）以及关注（`watch`）均独立于任务 `status` 状态保存，不混成任务状态。

验收分为三档（建单时由 `reviewer` 指定，省略时默认为用户验收；用户可随时调整）：

1. **成员独立验收（`reviewer: { kind: "member", memberId }`）**：验收者必须不是该任务任何有效派工或提交的参与执行者。执行者提交（`submit`）带摘要（需要合并时须带 7～40 位十六进制 `commitSha`）后进入 `review` 并唤醒验收者；验收通过（`approve`）后若 `mergeRequired: true` 由**验收者**运行 `ship` 合入目标分支并完成 `merged`，无需合并则直接 `completed`。
2. **自查（`reviewer: { kind: "self" }`）**：适用于纯文档、小范围改动、低风险测试或常规设计任务。执行者在 `submit` 的 `summary` 写明检查命令与结果，Hub 在同一事务写入一条标明 `self: true` 的通过记录并直接将任务推进至 `completed`（若 `mergeRequired: true`，则由**执行者**运行 `ship` 完成合并）。任务进入 `review` 后不得再改回自查。
3. **用户验收（`reviewer: { kind: "user" }`）**：适用于界面效果确认或需人工亲自把关的改动。`submit` 后停在 `review` 等用户在界面审批；通过后若需要合并则由**执行者**运行 `ship`（或经网页提交手动标记）。

- **依赖关系**：任务通过 `dependencyIds` 声明前置依赖；所有前置结果有效且 `mergeRequired: true` 的前置均已 `merged` 后，下游任务方可执行。

## 接管（`takeover`）与重开

- **验收者接手（`takeover`）**：仅针对当前处于成员验收档且存在明确成员验收者的任务（在待开工、执行中或待验收状态均可发起，不要求原验收者在线），把执行权移交**给那位原成员验收者**本人（而**不是**改派给任意在线成员）。接管后后续验收人若省略则默认转为 `{ kind: "user" }`（仅在用户发起接管或本群已开启 `takeoverSelfReview` 设置时可指定 `{ kind: "self" }`，否则须指定未参与该任务的其他成员）。
- 若已结束或已取消的任务需要重新处理，可通过 `reopen` 恢复执行流转。

## 任务关联本地 Git 分支

任务详情可以关联一个本地 Git 仓库和分支，用来定位工作；验收和 `ship` 仍以各自记录的提交 SHA 为准。

- **手动关联**：用户在任务详情里选仓库（候选来自本群成员的项目目录，同一仓库的多个 worktree 只列一次，也可以填仓库、worktree 或子目录的绝对路径）和本地分支（也可以填还没创建的合法分支名）；当前执行者可以用 `task_action set_git_branch` 登记分支。传 `null` 清除。任务历史保留每次变化的前后值。
- **提交时自动关联**：执行者经 MCP `task_action submit` 带 `commitSha` 提交时，Hub 用只读 git 找末端正好是这个提交的本地分支（`refs/heads/`）：任务已有关联就在关联的仓库里找，没有才在执行者自己的项目目录里找。恰好一条时关联它并标“自动”；手动关联永远保留（分支不包含这个提交时只提醒）；原来的自动关联不再适用时清除。提交结果里的 `gitBranch` 写明结果（`linked`、`kept`、`cleared`、`not_linked`）和原因，例如 `no_branch`、`several_branches`、`timeout`。
- 查找有总时限（1.5 秒）和并发上限，任何失败都不影响提交本身，只是不关联。手动设置会把自动关联变成手动；清除后下一次提交会重新自动关联。
- 关联写进任务的本机仓库路径对本群成员可见，和手动关联相同。

## 验收批次

验收批次是一组由同一个验收者（用户或一名成员）在**全部提交后一起验收**、**全部通过后一起合并**的任务，适合一串互相依赖的任务，避免验收者被反复唤醒、检查跑很多遍。批次显示为 `B3` 这样的编号；不在批次里的任务行为不变。

- **建立和加入**：用户、成员或有相应授权的协调员可以建批次（`manage_batch create`），验收者不能是自查、启用中的协调员或隐身成员。任务在建单时带 `batchId`，或开工前用 `manage_batch add` 加入；只有需要合并、不是自查的任务能加入，加入后验收者就是批次的验收者。批次有了第一条验收记录后不再接受新任务。开工前或取消后可以移出；取消批次时任务回到普通流程，提交和记录都保留。
- **提交与“齐了”**：批次里的任务提交后进入待验收，但成员验收者只计未读、不被唤醒。所有没取消的任务都已提交（或已通过且结果有效）时，在让批次变齐的那个动作里给验收者发**一条**唤醒通知，列出每个任务和被审提交。没齐时成员验收者验收会得到 `BATCH_INCOMPLETE`，并列出还差哪些；用户随时可以验收。每个任务仍各自给结论，退回只退回那一个任务。
- **批次内依赖**：同一批次里的前置任务只要有有效提交就算就绪，下游可以接着上游的分支开工；`get_task` 的依赖里给出 `batchBase`（上游的提交号和关联的分支）。上游重新提交后，下游待验收的提交过期、已通过的结果失效，下游要用 `expectedDependencyVersions` 声明新版本重新提交。批次外的依赖仍要等前置合并。
- **一起合并**：批次里的任务不能单独 ship。全部通过后，`get_batch`（以及最后一个通过动作的结果）给运行者一条批次 ship 命令：成员验收者通过了全部任务时由它运行，否则由按依赖顺序最后一个任务的执行者运行。脚本在临时 worktree 里按依赖顺序逐个合并被审提交，只建**一个**合并提交（每个任务一行 `Reviewed-by`），检查只跑一遍，通过才快进目标分支，Hub 核实后把所有任务一起记为已合并。冲突时只退回冲突的那个任务；检查两次都失败时退回依赖链末端的任务。
- **网页**：任务页签里批次各占一组，显示进度、验收者和“批次详情”；新建任务表单在有可加入的批次时可以选择批次。

## ship 与发布

审查通过后，由成员用自己的权限运行 `scripts/ship.ts` 把被审提交合进目标分支（仓库的 `git config orrery.shipBranch`，未配置时为 `main`），Hub 不写 git。命令由 `task_action review` 的通过结果或 `get_task` 给出（谁运行见上面三档验收）；它带 Hub 签发的票据，脚本在锁内、临时 worktree 里 `merge --no-ff`，跑仓库 `.premerge/checks.json` 声明的检查（只改文档时跳过，失败自动重跑一次；重跑前会暂存首轮 `.tmp/test-logs/*.log` 与 `.tmp/*-shots/` 截图，若两次都失败，会在删除临时 worktree 前按 `attempt-1/`、`attempt-2/` 保留到 `.tmp/ship-failures/`，最多留最近 10 次并脱敏令牌/票据，同时在本地标准错误输出保存路径，在共享失败详情里附上失败摘要、相对路径及脱敏路径前缀），通过才快进目标分支，只有目标是 `main` 时才自动推送。冲突或检查失败时目标分支不动，任务退回执行者，群里说明原因，可展开查看失败详情。Hub 收到结果后用只读 git 核实再记为已合并。

`node scripts/ship.ts --release --user-approved …` 把 ship 的目标分支合进 `main`（发布），用同一把锁和同样的检查，不经过 Hub；只应在用户明确要求发布时运行。

## 消息分级、未读与通知合批

Hub 按发送者与 `@` 形式分别决定谁计入未读、谁被唤醒执行：

| 发送动作 | 谁计入未读 | 谁被唤醒执行 | 说明 |
|---|---|---|---|
| 群员发群聊 `@成员` | 被点名者（`mention`） | 被点名者（除非 `fyi: true`） | 标准点名协作 |
| 群员发群聊 `@all` | 全体在群成员（未显式点名者记 `broadcast`） | **仅正文中显式 `@名字` 点到的成员** | 纯 `@all` 不唤醒任何成员 |
| 群员带 `fyi: true` 发言 | 被点名者 | 一般不唤醒；**例外**：若设了 `replyTo` 且原提问者仍是正文显式点到的活跃成员，则该提问者**仍被唤醒**（结果返回 `fyiOverridden`） | 回答别人问题时禁止设 `fyi: true` |
| 群员发群聊无 `@` | 不计入他人未读（协调员也不计） | 不唤醒 | 仅留群聊历史，可用 `history: true` 查看 |
| 用户未 `@` 发言 | 全群在群成员（`user` 类别） | 按群内路由规则投递 | 无 `@` 时若启用协调员会兜底转协调员 |
| 成员页/MCP 带 `to` 指定发送 | 指定收件人 | 指定收件人 | 忽略正文中 `@` 解析 |
| 已读回执（`ack_messages`） | 原发送者读取历史可见 | 不唤醒、不写系统消息 | 回执（👍）即收到，不为确认单独水聊 |

- **通知合批**：任务进度等系统通知采用 `noticeWindowMs`（2 秒）合批，与常规聊天 `messageWindowMs`（10 秒）错峰；单批上限 `32` 条，每成员每小时通知批数上限 `maxNoticeBatchesPerHour = 300`。
- **工具后未读提示**：合法 MCP 调用末尾及可选 [未读提示钩子](adapters/unread-hook.md) 会按 4 个桶（`mention`、`user`、`broadcast`、`task_notice`）在未读分项计数有变化时展示计数提示。

## 隐身、标签、关注与交接

- **成员隐身（`hiddenAt`）**：隐身**不只是前端隐藏**——Hub 会阻断所有发给隐身成员的消息投递、所有 MCP 工具调用（含读消息）一律只返回提示而不执行任何动作、不可接收新派工或被 `@` 点名，且除用户与启用中的协调员外其他成员不可见；原有消息历史与既有任务仍保留在库中。
- **全局标签库与关注**：跨群维护彩色标签组（`task_label_groups` / `task_labels`）；成员通过 `watch` / `unwatch` 关注关联任务并在结束时收到单条系统提醒。
- **协调员委托权限与交接**：支持配置协调员的 8 项管理开关及空闲/额度告警；成员下线换会话可通过 `GET /api/members/:id/handover` 导出结构化交接摘要。
- **回收站与彻底清理**：删除的集群进回收站，支持 `restore`；`purge` 在事务内彻底删除关联记录及无主文件。
